Yes. For this take-home, your goal is not only to make an LLM answer crossword clues. You should show an **agent that solves the crossword as a constraint problem**, evaluates itself, corrects mistakes, and produces measurable results.

### Recommended project flow

1. **Set up Token Factory**
   Sign up for [Token Factory](https://tokenfactory.nebius.com/?utm_source=chatgpt.com) and complete the required $0 card authorization. Then activate the provided [$100 candidate credit](https://nebius.com/promo-code?utm_promo_event_code=tokenfactory-credits-100&utm_promo_code_type=Token_Factory&utm_promo_activation_code=TOKENFACTORY-100-COKE&utm_promo_campaign_id=candidate-interviews&utm_source=chatgpt.com). You can use the hosted model API as the reasoning model for the agent.

2. **Create the crossword input format**
   Start simple. Give the program a grid plus Across/Down clues. Internally represent every answer with `clue`, `direction`, `length`, `start position`, `current pattern`, and intersecting words. For example, a 5-letter answer with known letters could have a pattern like `C _ A _ E`.

3. **Build a baseline solver first**
   Ask the LLM to generate perhaps **3–5 candidate answers per clue**, constrained by answer length. Store the candidates with confidence scores. This gives you a simple baseline you can later compare against your agent.

4. **Make it actually agentic**
   This is the important part. I would use a loop like:

```text
Crossword
   ↓
Parse grid + clues
   ↓
Pick highest-confidence clue
   ↓
LLM generates candidate answers
   ↓
Check length + known letters
   ↓
Place best candidate
   ↓
Propagate crossing letters
   ↓
Re-evaluate affected clues
   ↓
Conflict?
 ┌─Yes → reconsider / backtrack
 │
 No
 ↓
Continue
   ↓
Validate complete puzzle
```

The key idea is that **the model proposes; deterministic code verifies**. For example, if Across suggests `APPLE` but a crossing Down answer requires the third character to be `R`, your agent should detect the contradiction instead of blindly accepting the LLM response.

5. **Add tools to the agent**
   Give it functions such as `get_unsolved_clues()`, `get_pattern(clue_id)`, `generate_candidates()`, `place_answer()`, `check_crossings()`, `remove_answer()` and `backtrack()`. A strong implementation selects easy/high-confidence clues first, propagates their letters, and uses those new constraints to solve harder clues.

6. **Add self-correction**
   Don't immediately lock every answer. Keep candidate lists and confidence scores. If later answers create conflicts, identify the lowest-confidence conflicting answer, remove it, regenerate candidates using the new letter pattern, and continue. Put a maximum iteration/backtracking limit so the agent cannot loop forever.

7. **Build evaluation properly**
   Prepare a dataset of crossword puzzles where you know the correct answers. Report at least **word accuracy**, **letter accuracy**, **full-puzzle solve rate**, average API calls/tokens, latency, and cost. Also separate results by clue difficulty if possible.

A particularly good FDE experiment would compare three versions:

| Approach | What you're testing |
|---|---|
| LLM only | Baseline |
| LLM + crossing constraints | Value of deterministic validation |
| Agent + constraints + backtracking | Value of the complete agent |

For example, your final README could report something like `LLM baseline: 63% word accuracy → constraints: 78% → full agent: 86%`. **Use your actual measured numbers**, not invented results.
